mcpd Architecture Review

A modular-monolith MCP host that gates every infrastructure mutation behind a durable approval state machine. The plugin model, the SQLite-as-authority rule, the outbox, and the two-step proposal flow are all correct and should be built as specified. Three things need to change before code is written, and one of the cnMaestro assumptions in the brief does not survive contact with the actual API.

01

Architecture review

The brief asked to be challenged rather than agreed with. Six things are worth arguing about; the rest of the design is sound and I would build it as written.

1.1  Embedded NATS is not earned at version one — defer it

This is the change I would push hardest for. The brief's own invariants dismantle the case for a broker on a single node:

  • SQLite is the sole authority for whether a mutation is approved.
  • The transactional outbox already provides durable, restart-safe delivery.
  • The executor must reload and revalidate everything from SQLite on receipt, so the message carries no trust and no payload that matters.
  • Version one is one process on one VM.

Put those together and JetStream's job reduces to a single sentence: "an operation became approved; wake the executor." On one node that is a Go channel plus a claim query with a polling fallback — roughly fifty lines, trivially testable, zero dependencies.

The cost side is not small. An embedded broker brings a second on-disk store to fsync and back up, a second corruption-recovery story, stream and consumer configuration that can drift from code, redelivery loops to bound, and an extra layer threaded through every integration test. It is a lot of operational surface to buy a wake-up signal.

The tell

The natural embedded configuration is DontListen: true — no TCP socket at all, which I verified works. But that setting is definitionally a broker you cannot publish to or consume from outside the process. Embedding with the listener enabled, on the other hand, is just running NATS with a worse operational story than a separate nats-server unit: no independent restart, no independent version, no nats CLI against a stable endpoint.

Recommendation. Build the EventBus interface, the subject taxonomy, the event envelope, and the outbox table exactly as specified — that is the entire portability layer and it costs nothing. Ship one implementation in v1: an in-process dispatcher fed by the outbox table. Add the JetStream implementation of the same interface the day a second consumer exists, whether that is a second mcpd instance or an external system that wants the event feed. Section 7 specifies both so the second one is a drop-in.

I have written Section 7 as though NATS will be added, because the subject and stream design has to be fixed now to stay portable. What I am arguing against is running the broker before anything reads from it.

1.2  The plugin interface is too large and mixes two concerns

The six-method interface in the brief bundles registration with lifecycle, which forces every plugin to implement Start and Shutdown whether or not it has background work. Most will not. Split it: a two-method Plugin, plus optional capability interfaces the host discovers by type assertion. Section 4 has the full contract.

Related: Services as a wide interface handed to plugins is a service locator, and the brief already hedges on it. Replace it with a concrete Deps struct carrying exactly the typed dependencies a plugin may touch — and note what is deliberately absent from it: no OperationService, no AuditService, no database handle. A plugin that cannot reach operation state cannot corrupt it, and that is a structural guarantee rather than a code-review convention.

1.3  The state machine is missing its two most important transitions

Both gaps are safety-critical.

approved → expired. The brief expires proposals but not approvals. Without a second deadline, an approval granted three weeks ago is still executable today against a network that has since changed underneath it. Approval must carry its own short expiry, separate from the proposal's.

executing → indeterminate. This is the single most valuable addition. If the process dies between issuing an upstream POST and recording its result, the truthful answer is that we do not know whether the mutation applied. Recording that as failed is a lie that invites a retry, and the retry double-applies. It needs its own state, its own reconciler, and a rule that nothing automatically leaves it — the reconciler observes upstream and resolves to succeeded or failed, or a human does.

1.4  Separation of duties is unenforceable under the likely v1 identity model

"An operator cannot approve their own high-risk operation" requires two distinguishable principals. If v1 ships with a single static bearer token — the pragmatic starting point — there is exactly one principal, and the four-eyes rule silently degrades to no rule at all while the config file still claims it is on.

Fail closed

Make require_distinct_approver a policy that refuses rather than degrades. If the active authentication mode cannot distinguish the approver from the requester, operations at that risk level are rejected at proposal time with an explicit reason. A capability the system cannot honour must not be silently disabled.

1.5  Read tools have no threat model in the brief

The write path is well defended; reads are treated as harmless. They are not. Device names, client hostnames, SSIDs, and alarm text all originate outside the trust boundary and flow straight into the model's context — that is a prompt-injection channel into a system that also holds approval tools. Two mitigations, both cheap:

  • Mark untrusted upstream text as data when rendering tool results, and never interpolate it into anything the host itself parses.
  • Rate-limit reads per principal. cnMaestro's token is account-wide and its throttling is undocumented; an unbounded model loop will find that limit for you.

1.6  Adopt the stateless transport from day one

go-sdk v1.7.0 implements protocol 2026-07-28, which removes the initialize handshake and protocol-level sessions in favour of per-request metadata. The SDK exposes this as StreamableHTTPOptions{Stateless: true}.

Turn it on. It eliminates session affinity, which is precisely the thing that would otherwise make "multiple mcpd instances" a redesign rather than a config change. The trade-off is that server-to-client requests are rejected, so elicitation is unavailable — which only reinforces a decision the brief already made correctly: approval is a second tool call, not an interactive prompt. An elicitation-based approval would have put the authorization decision inside the model's turn, which is exactly the boundary violation the whole design exists to prevent.

1.7  Confirmed as specified

Modular monolith

Correct for this scale. One binary, one database, strong internal boundaries. Nothing here needs a network hop between components.

Endpoint per plugin

Correct, and cheap to implement — the SDK's NewStreamableHTTPHandler(getServer func(*http.Request) *Server, …) is exactly the hook for it.

Compile-time registration

Correct. Go's plugin package would buy nothing here and cost static linking, which is the deployment story.

synchronous = FULL

Correct and verified. Under WAL, NORMAL can lose the last transactions on power loss. Write volume is human-paced, so the cost is irrelevant.

Typed mutations only

Correct, and Section 10 shows why it matters more than expected: cnMaestro ships a remote-CLI endpoint that must be permanently blocked.

modernc.org/sqlite

Correct. Active, pure Go, SQLite 3.53.3, static binary verified. ncruces/go-sqlite3 benchmarks faster on reads but adds a wasm runtime for a workload that is not read-bound.

One addition

Under WAL, database/sql with a shared pool will produce SQLITE_BUSY as soon as two goroutines write. Open two handles against the same file: a reader pool, and a writer with SetMaxOpenConns(1). All repository writes go through the writer. This is the standard fix and it is much easier to build in now than to retrofit.

Reading the diagram

Two arrows leave the plugin box and they are not symmetric. Read tools call the upstream API directly. Mutation specs only ever describe a change to the operations service; the plugin's Apply is invoked later by the executor, from the other side of the database, after the operation has been reloaded and revalidated. A plugin can never move an operation through the state machine.

04

Plugin contract

Two required methods. Everything else is an optional capability interface or a free generic function, because Go interfaces cannot carry type parameters.

internal/plugins/plugin.go
package plugins

// Plugin is the minimum contract. A plugin that only exposes read tools
// implements exactly these two methods and nothing else.
type Plugin interface {
	Descriptor() Descriptor
	Register(ctx context.Context, r *Registry) error
}

type Descriptor struct {
	Name        string // "cnmaestro"; [a-z][a-z0-9_-]*; unique; forms /mcp/<name>
	Version     string
	Title       string // human label for the MCP server
	Description string // becomes ServerOptions.Instructions
}

// Optional capabilities, discovered by type assertion. Implement only what
// you need — most plugins need none of them.
type Starter interface{ Start(ctx context.Context) error }
type Stopper interface{ Shutdown(ctx context.Context) error }
type Checker interface{ Check(ctx context.Context) Health }

type Health struct {
	State   HealthState // Healthy | Degraded | Unhealthy
	Message string      // MUST be redaction-safe; surfaced on /health/ready
	Checked time.Time
}
internal/plugins/registry.go — what a plugin is handed
package plugins

// Registry is concrete, not an interface, so registration can use generics.
type Registry struct{ /* host-owned; unexported fields */ }

// Tool registers a read-only tool. In/Out schemas are derived from the types.
// The host adds the plugin name prefix, ReadOnlyHint, authorization, rate
// limiting, correlation IDs and audit around the handler.
func Tool[In, Out any](r *Registry, spec ToolSpec, fn ToolFunc[In, Out])

// Mutation registers an approval-gated write. This does NOT create an
// executable tool — it creates a *propose* tool. Execution happens later,
// from the executor, only after the operations service says so.
func Mutation[P, S any](r *Registry, spec MutationSpec, h MutationHandler[P, S])

type ToolSpec struct {
	Name        string // bare; host prefixes with plugin name
	Title       string
	Description string
	Scope       auth.Scope // minimum role required
}

// Deps is what a plugin receives at construction. Note what is ABSENT:
// no OperationService, no AuditService, no *sql.DB, no KV. A plugin that
// cannot reach operation state cannot corrupt it.
type Deps struct {
	Log     *slog.Logger  // pre-tagged with plugin=<name>
	Store   Store         // namespaced KV over plugin_state; small values only
	Events  Publisher     // namespaced to mcp.plugin.<name>.> — cannot forge
	Secrets SecretSource  // resolves refs; values never enter config structs
	HTTP    *http.Client  // bounded conns, timeouts, redaction transport
	Now     func() time.Time
}

The mutation contract

This is the part worth the most care. A mutation is not one function but three, and separating them is what makes precondition checking, verification, and at-most-once execution possible at all.

internal/plugins/mutation.go
package plugins

type MutationSpec struct {
	Action      string          // "device.set_radio_channel"
	Title       string
	Description string
	Risk        operations.RiskLevel // default; policy may raise it, never lower
	Scope       auth.Scope
	Reversible  bool            // may a rollback operation be generated?
}

// MutationHandler[P,S]: P is the typed parameter struct, S the typed
// observable state of the target.
type MutationHandler[P, S any] interface {

	// Plan validates params and reads current state. It MUST NOT mutate.
	// Called twice: once at proposal (to capture `before` and impact) and
	// again immediately before Apply (to detect drift). The host compares
	// the two Preconditions and fails with PRECONDITION_CHANGED on mismatch.
	Plan(ctx context.Context, p P) (Plan[S], error)

	// Apply performs the upstream write. Called at most once per attempt,
	// only from the executor, only after the state machine granted a claim.
	// On an ambiguous failure it MUST return ErrIndeterminate rather than an
	// error that implies the write did not happen.
	Apply(ctx context.Context, p P, plan Plan[S]) (ApplyResult, error)

	// Observe re-reads state for verification and for reconciling
	// indeterminate outcomes. MUST NOT mutate.
	Observe(ctx context.Context, p P) (S, error)
}

type Plan[S any] struct {
	Before        S              // observed state, persisted immutably
	Desired       S              // what Apply intends to produce
	Preconditions map[string]any // ETag / revision / field snapshot
	Changes       []Change       // field, from, to — shown to the approver
	Impact        string         // plain language; shown to the approver
	Rollback      json.RawMessage// params for the inverse mutation, if any
	RiskOverride  *operations.RiskLevel // may RAISE risk for these params only
}

type ApplyResult struct {
	UpstreamRef string // job id / change id, for reconciliation
	Async       bool   // true ⇒ success requires Observe, not HTTP 200
}
Why three methods and not one

Plan running twice is what turns "optimistic concurrency" from an aspiration into a mechanism — the same code path produces the snapshot shown to the approver and the snapshot checked at execution, so they cannot drift apart. Observe existing separately is what lets the verifier and the reconciler share one implementation. And Apply being the only mutating method means the audit rule is mechanical: an audit row is written around exactly one call site.

06

SQLite schema

Timestamps are Unix milliseconds as INTEGER — sortable, comparable in SQL, and free of the text-format ambiguity that eventually bites ISO-8601-in-TEXT. JSON columns hold canonical (sorted-key, no-whitespace) form so hashes are reproducible.

Connection setup

Pragmas — all verified against modernc.org/sqlite v1.57.0
journal_mode = WAL      // concurrent readers alongside one writer
foreign_keys = ON       // off by default in SQLite; must be set per connection
synchronous = FULL      // approval durability > write throughput (brief agrees)
busy_timeout = 5000     // tolerate brief writer contention before erroring
wal_autocheckpoint=1000 // bound WAL growth on a long-lived process

// Two handles on the same file — see §1.7:
readDB.SetMaxOpenConns(max(4, runtime.NumCPU()))
writeDB.SetMaxOpenConns(1)   // serialise writers in Go, not via SQLITE_BUSY

Transaction boundaries

Six transactions cover every write in the system. Anything not on this list is a bug.

TxOperationStatements — all or nothing
TX-1ProposeINSERT operations (state pending_approval) + INSERT idempotency_records + transition + audit + outbox mcp.operation.proposed
TX-2Approve / RejectUPDATE operations SET state=… WHERE id=? AND state='pending_approval' — must affect 1 row — + transition + audit + outbox
TX-3ClaimGuarded UPDATE … SET state='executing', lease_owner=?, lease_expires_at=?, attempt_count=attempt_count+1 WHERE id=? AND state='approved' AND payload_hash=? AND approval_expires_at>? + INSERT execution_attempts + transition + audit + outbox. Zero rows affected means another worker won; abandon silently.
TX-4SettleUPDATE operations to a terminal or indeterminate state + UPDATE execution_attempts + transition + audit + outbox
TX-5Outbox ackUPDATE outbox_events SET published_at=? — its own transaction, deliberately (§8)
TX-6Reap / CancelGuarded UPDATE per row + transition + audit + outbox. Batched, but one transaction per operation so a single bad row cannot stall the sweep.
The rule that makes it work

Every one of these writes its outbox row inside the same transaction as the state change. There is no code path that changes state without enqueueing an event, and none that enqueues an event without changing state. That is the entire dual-write defence, and it is enforced by there being exactly one UnitOfWork API rather than by discipline.

NATS design

Specified in full so it stays portable, and — per §1.1 — recommended for v2 rather than v1. The subject taxonomy and event envelope go in now regardless; they are what make the swap a configuration change.

If and when JetStream is enabled

Streams
  • MCP_OPERATIONS — mcp.operation.>, file storage, limits retention, MaxAge 30d, Duplicates 2h
  • MCP_PLUGINS — mcp.plugin.>, file storage, MaxAge 7d, Duplicates 2h

The duplicate window must comfortably exceed the outbox's maximum retry backoff, or a slow retry re-publishes as a genuinely new message.

Consumers — durable, explicit ack
  • mcpd-executor — filter mcp.operation.approved, AckWait 60s, MaxDeliver 5, MaxAckPending = worker pool size
  • mcpd-reconciler — filter mcp.operation.indeterminate, long AckWait, low concurrency

On MaxDeliver exhaustion, terminate the message and record it — SQLite still holds the truth, so a dropped notification costs latency, never correctness.

KV buckets — coordination only
  • mcpd_leases — TTL 60s. Create to claim, Update(rev) to renew. Both verified: second claim and stale-revision renewal both fail correctly.
  • mcpd_runtime — TTL 30s. Instance heartbeat, plugin health, scheduler leadership.
Core NATS

Nothing at v1. Reserved for genuinely ephemeral fan-out where loss is acceptable and durability would be wrong — live log tailing, UI push. Never for anything a decision depends on.

What must never touch NATS

Explicit exclusions

Approval authority · operation state · the audit log · payload hashes · idempotency records · configuration · secrets · any value read on the critical path of an authorization decision.

The KV lease is supplemental. If the KV bucket vanished entirely, TX-3's compare-and-set still guarantees at-most-once execution — the lease only reduces wasted work across instances. Any design where losing the lease bucket causes a double-apply has inverted the authority model.

08

Transactional outbox

Publisher lifecycle
  STARTING ──► RUNNING ◄──────► BACKOFF        (exponential + jitter,
                 │                               capped well below the
                 │                               stream duplicate window)
                 ▼
             DRAINING ──► STOPPED

RUNNING loop:
  1. SELECT … WHERE published_at IS NULL AND next_attempt_at <= now
       ORDER BY seq LIMIT batch        -- ordered by seq: per-subject order held
  2. for each: Publish(ctx, event)      -- dedup key = event_id
  3. on ack:  TX-5  UPDATE published_at = now
  4. on err:  attempts++, next_attempt_at = now + backoff(attempts), record error
  5. idle ⇒ wait on notify-channel or 5s tick, whichever fires first

Failure matrix

ScenarioWhat actually happensResolution
SQLite commits, publish fails State change and outbox row are durable. The event is simply not out yet. Row stays published_at IS NULL; the publisher retries with backoff until it succeeds. NO LOSS
Publish succeeds, ack lost The broker has the message; we never learned it. The row still looks pending, so we republish. WithMsgID(event_id) against the stream's duplicate window — the republish is discarded server-side and returns dup=true, which we treat as success. VERIFIED
Duplicate delivery to the consumer Redelivery after AckWait, or an at-least-once path we cannot close. The consumer carries no authority. It reloads from SQLite and attempts TX-3's guarded claim; the second delivery matches zero rows because the state is no longer approved, and it acks and exits. HARMLESS
Process restart mid-publish Unpublished rows survive; in-flight publishes may or may not have landed. The drain query is the whole recovery procedure — there is no separate recovery path to get wrong. Anything that did land is caught by the dedup window; anything that did not is republished. SELF-HEALING
Broker down for hours Outbox backlog grows. Proposals, approvals, and audit continue normally — none of them depend on the bus. The executor's polling fallback keeps approved work moving without any event at all. Backlog depth is a readiness signal, not a liveness one. DEGRADED, CORRECT
Backoff exceeds the duplicate window A very late republish is no longer recognised as a duplicate and lands twice. The only genuinely dangerous case, and it is a configuration error, not a runtime one: cap backoff at a fraction of Duplicates and assert the relationship at startup. Even then, consumer idempotency (row 3) contains it. ASSERT AT BOOT
Why TX-5 is deliberately separate

Marking an event published is not part of the business transaction. Folding it in would mean holding a write transaction open across a network call — turning broker latency into database contention, and a broker stall into a total write outage. Keeping it separate is what buys at-least-once instead of exactly-once, and at-least-once is fine precisely because the consumer has no authority.

Graceful shutdown

Reverse-ordered drain — total budget under TimeoutStopSec=45
 1. /health/ready → 503            proxy stops routing; live stays 200
 2. stop accepting new MCP requests, drain in-flight tool calls   ≤10s
 3. operations service refuses new proposals and approvals
 4. stop consumers; stop claiming new work
 5. in-flight executions: wait ≤20s
       ├─ settled       → TX-4 normally
       └─ still running → TX-4 to `indeterminate`, lease left to expire
 6. flush outbox, best effort                                     ≤5s
 7. plugin Shutdown(ctx), reverse registration order
 8. drain NATS if enabled; close reader pool, then writer
 9. checkpoint WAL; close; exit 0

Step 5 is the one that matters. An execution interrupted by shutdown must land in indeterminate, not failed — the same reasoning as a crash, and the reason that state exists. Writing failed here would make an ordinary systemctl restart during a change window a source of double-applied mutations.

cnMaestro API findings

Sourced from the OpenAPI 3.0 specification that Cambium's own documentation viewer loads at docs.cloud.cambiumnetworks.com/api/5.0.1/yaml/schemas/v2/ — the machine-readable spec, not the rendered page. Everything marked CONFIRMED was read from that spec. Nothing here is inferred from model knowledge.

The headline finding

The brief's motivating example does not map to the API

There is no radio.set_channel endpoint, and no radio resource of any kind. Changing an AP's channel is a device configuration override: PUT /api/v2/devices/{mac} with a body containing overrides.radios[]. Three consequences follow, and each one changes the design:

channel is a string enum — "36", "149", "auto" — not an integer. The brief's Channel int would fail validation. Same for power. Only channel_width is an integer.

It is a configuration intent, applied asynchronously by cnMaestro to the device. HTTP 200 means the override was accepted, not that the radio moved. Verification is genuinely two-phase, and ApplyResult.Async exists for exactly this.

Whether PUT overrides merges or replaces is undocumented — and it is the single highest-risk unknown in this integration. If it replaces, a channel change silently discards every other override on that AP. No amount of approval workflow catches that, because the approver would be shown a correct one-field diff while the request wipes six other fields. This must be settled against a real controller before any write ships.

Proposed v1 mutation surface

Two mutations, both low-blast-radius, both verifiable, both exercising a different part of the machinery.

Plan reads GET /devices/{mac} for current overrides. Apply issues the PUT. Observe re-reads and compares. Exercises async verification and precondition drift.

type RebootDevice struct {
  MAC    string `json:"mac"`
  Reason string `json:"reason"`
}

The simplest possible mutation, and the sharpest test of the indeterminate path: no idempotency key upstream, so an ambiguous POST genuinely cannot be retried. Exercises ErrIndeterminate and the reconciler.

Must be answered against a live controller before writes ship

  1. Does PUT /devices/{mac} merge or replace the overrides object? Everything else is secondary to this.
  2. What does GET /devices/{mac} actually return — configured overrides, effective configuration, or both? Verification is meaningless without knowing which.
  3. Where does the operating channel appear, as distinct from the configured one? Likely /devices/{mac}/statistics, unconfirmed.
  4. Does any response carry an ETag, revision, or generation? If not, optimistic concurrency degrades to field-snapshot comparison, which is weaker and must be documented as such.
  5. What is the actual 429 threshold, and is Retry-After returned?
  6. What is the maximum accepted limit, and what is the list-response envelope?
  7. How long does a radio override take to reach the device? This sets the verifier's backoff ceiling.
  8. Does the /configuration/commit 30-second auto-commit timer apply to device-level overrides, or only to AP-group and WLAN changes? If it applies to overrides, the approval gate needs rethinking for that path.

Stop point

Sections 1–10 complete. No implementation code has been written; the repository contains only this document.

Three decisions need to be made before the first commit:

  1. Embedded NATS in v1, or the in-process bus? (§1.1) — this is the one that changes the most code.
  2. Identity model for v1. (§1.4) — static token with high/critical mutations refused, or OAuth with per-user principals from the start.
  3. Is a live cnMaestro controller available for the eight questions above? (§10) — the cnMaestro write path cannot be responsibly built without it, though the entire host, plugin framework, storage layer, approval engine, and cnMaestro read path can all proceed in parallel.

Once those are settled, the build order is: host and plugin framework → SQLite storage and migrations → operations service and state machine → outbox and event bus → cnMaestro reads → cnMaestro mutations.
